# 求解结果解释

## 证据顺序与任务绑定

按以下顺序使用信息：

1. `gateway.solver_jobs.get_detail` 返回的任务状态、失败信息和公开约束摘要；该 MCP 工具是基础详情投影，不返回 `result_summary`、`engine_view` 或 `pending_engine_view`；
2. `gateway.solver_jobs.get_summary` 返回的 `result_score` 与 `result_summary`；
3. `gateway.image_versions.get_result_summary_schema` 对摘要字段的定义；
4. 明确绑定该任务的当前会话已确认输入草稿，或 `gateway.solver_jobs.get_scenario` 返回且已核对来源任务 ID 的求解前场景；
5. 用户额外提供并确认所属任务的脱敏业务信息。

不要调用管理员接口、直接 REST 场景回放、引擎／归档接口或完整结果下载。核对已有工作量或原安排需要历史输入时，可以按该任务 ID 调用 `gateway.solver_jobs.get_scenario` 获取 Gateway 派生场景；不把当前草稿或另一任务输入冒充历史输入。工具缺失、无权限或读取失败时，可以确认结果中的数量与归属，但不能猜测哪些是已有单或宣称已验证原安排保留。

地图、Gantt、工程师路线和规划回放按 [MCP Apps 只读展示](mcp-apps-ui.md) 使用 Gateway 授权工具。只读规划回放不同于直接调用引擎/归档接口；不要为展示访问上述禁止接口。UI 专用数据不一定进入模型上下文，页面有图不代表 Agent 已获得全部分析证据。无 UI 时保留摘要和网页入口。

## 主动核查后的业务回答

先定位任务及用户点名对象，再取得该任务的场景、摘要和对应 ImageVersion 的摘要 Schema。能通过只读工具补齐的信息先查；核查过程留在内部，对外采用“结论＋关键依据”，说清即止。每句话都应直接回答用户实际提出的疑问或支持该结论，不替用户提出其他疑问、不预设用户有误解。按下文“回答结构”选择最小充分证据，而不是汇报所有查到的内容；用户追问的细节再单独展开。

默认使用姓名、地址和服务类型识别对象，不展示工单编号；同类对象无法区分且影响结论时才加短编号。普通业务问答用“全天单量均衡”“每天最多几单”等业务称谓，技术字段、原始得分和关联配置留给技术追问。时间只在本题需要且语义已核实时使用。涉及真正影响结论的缺口时，回答已核实部分并点明具体待核对项，不用泛泛的“没有返回原因”代替解释；无需在结尾重复结论或附无关尾注。

## 问题范围守恒与目标守恒

- 核对已有单量时不转而批评同址拆分；解释同址拆分时不自行制定目标。评价基于已确认规则，不能擅自改成“同址集中优先于均衡”等优先级，也不把正常拆分称为“过度拆分”。
- 没有可核对的先前错误，不生成“我之前遗漏了”等认错叙事；确有错误时核实后更正。不机械追加“不能证明最合理”、调参或对照求解建议。
- 简短不等于隐瞒异常。公开结果或用户证据发现漏单、超上限、预约变化、地图线路与排程时间不一致时，说明具体异常和影响；不能用 `succeeded` 或某个得分把它覆盖，不能声称 Skill 修改修复了引擎时间差。

## 默认业务摘要

用户没有询问具体归属、拆单或原因时，派单类成功结果按以下顺序展示；具体问题不套用此概览：

1. **整体是否可行**：优先使用摘要 Schema 定义的明确可行性字段；没有该字段时，可以结合公开得分作带依据的合理推断；
2. **派单完成情况**：派单成功数、未派单数，以及公开结果明确给出的未派原因；
3. **总体指标**：总里程、总时间、非零吨公里费用；缺失或不适用的指标不补造；
4. **工程师派单顺序**：按公开结果列出工程师、工单顺序、可用的到达时间和服务时间；
5. **详情入口**：链接文案使用“点击查看派单路线与排程详情”。

结合 `result_score`、`result_summary` 和摘要 Schema 判断及解释结论，默认不展示原始 hard/soft score。用户明确询问算法得分时再解释。任务状态为 `succeeded` 只代表求解过程成功，不能在缺少可行性证据时自动声称业务方案完全可行；已发现异常时不得笼统称“无约束冲突”。

## 证据等级

- **可确认事实**：响应中直接存在的状态、分配、时间、距离、数量、失败码，以及该任务已确认输入直接支持的业务事实。
- **合理推断**：说明分析条件和可核对的逻辑，以明确的业务判断表达，不要求每句使用可能性措辞；不说“引擎就是因为 X”，不声称拥有未提供的决策轨迹。
- **证据不足**：只说明影响当前问题的缺口及必要下一步。未派原因或指标没有公开字段时不根据行业经验或其他 ImageVersion 猜测。

只有 `gateway.solver_jobs.get_summary` 及对应摘要 Schema 明确返回 VRP0 的模型可见字段时，才分析已返回的硬资格、时序、位置、负载、公开目标和结果质量。地图 / Gantt 工具的 `_meta.gateway_ui.engine_view` 只供当前 App 绘图，不视为 Agent 已获得的分析证据。

### 时间字段语义

原始 score 是多目标得分，不是行驶时长。除非当前摘要 Schema 明确定义换算关系，不得将 soft 数值直接写成秒或分钟；矩阵 duration 与指标 duration 的单位也须明确定义，不能仅凭数值大小猜测。

解释时序、比较服务时段或核对预约保留前，必须读取当前任务对应 ImageVersion 的结果摘要 Schema，确认所用时间字段、`duration` 的语义、单位和时区。

- `arrival_time` / `departure_time` 不因字段名而自动等于服务开始 / 结束。不得仅凭 `duration` 自行用离开减时长推定服务开始；等待、服务与离开之间的关系只能依照当前 Schema 定义。
- 只有 Schema 明确给出语义与推导关系，且所需字段完整时，才计算服务起止；回答须标明推算及依据，不能将推算值冒充直接返回值。
- Schema 未明确服务起止或推导关系时，只报告实际返回的到达 / 离开变化，不计数为服务时段变化，也不声称原预约服务时间已保持。用户确实询问服务起止或预约保持时，指出具体哪些时段未能核对；只问人选或单量时不附此无关尾注。
- 原输入的预约时间、冻结规则、结果工单人员未变，都不能替代实际服务起止的核对。不能把计划要求当成结果证明。

## “已有工单算进去了吗，为什么还给他新单”

**内部核对**：使用明确绑定该任务的输入，按业务 ID 对照公开结果，区分已有、新派和全天合计。同址独立工单按真实业务口径计数，不默认折算。结果单量相同或安排可行，都不能单独证明已有工单已传入；输入中有而结果缺失时如实报告。缺少输入时只确认结果数量，并点明已有部分未能核对。

**回答结构**：先直接回答是否计入，再用点名工程师的小表或短句展示“已有 / 新派 / 全天合计”。用户同时问“为什么仍派给他”时，补一句其他工单不动条件下的转派影响，与已确认的全天负载目标对应；到此结束。表中数量已说明计入情况，无需再列旧单、新单编号或复述合计；仅问是否计入则无需补转派分析。

单量核对不能证明旧单时间未变。用户另外问原安排保留时，分别对照人员及语义已由 Schema 核实的服务开始和结束；依据下文重排规则回答。

## “为什么这张派给甲而不是乙”

**内部核对**：核对目标工单实际归属及用户点名的两个候选，检查同任务的技能、网点、班次、接单上限、已有及新增单量、相关前后地点，不只看日初出发点。指代不唯一时补问识别信息。涉及时间先按当前摘要 Schema 核实；时间语义不足时使用地点和计数证据，不推断服务时段可行性。矩阵与最终排程口径未统一时不拼接推算。

**回答结构**：先给证据支持的业务判断，再给关键依据。按证据选以下一种：

- 有已核实的排他限制：直接说明具体哪条规则排除了候选，给出对应业务事实。
- 没有排他证据：从“保持其他工单不动”时直接转单对已核实指标的影响切入，说明当前安排与已确认目标的关系；用户问距离时，再用双方相关地点回应，而不是重复日初位置。到此结束。

数字必须现场计算，不预设一定均衡或一定不宜转派；若两人相关地点相同，就陈述这个事实。用条件性比较表达明确结论：当前安排符合某目标、直接转单会改变某指标，是可以核实的判断；它们不等于求解器实际因此选中该人。内部资格核对不扩写成替代排程“能接/不能接”的总判断。候选人的地点应称为其相关安排，只有实际承接者才有该目标单的前后站。

局部单移假定其他分配不变，不等于全局重新求解；不把这项分析说成引擎唯一选人原因或全局最优证明。单项资格相符不证明替代排程整体可行。用户明确要求比较另一完整方案时才讨论对照求解，普通解释不得自动收费。

## “同址工单为什么分给多人”

**内部核对**：工单是否独立计数、是否同址、适用人员的单人当日上限及已有占用，确认限制确属硬规则。区分“是否必须拆分”和“为何选中当前人数 / 分法”。不同人员上限、已有占用或计数口径不同，按真实数据计算，不套统一阈值。

**回答结构**：已有充分超上限证据时，直接说明“该地址有多少单、每人一天最多接多少单，全给一人会超限，所以需要分给多人”，到此结束。计数口径在内部核实，不主动向用户解释计数概念。无需为这一算术事实创建对照任务；实际分配名单、关联配置等留待用户追问。

该证据不证明当前分给多少人最优或最少。不要把“至少需要拆分”改成“必须按当前分法拆分”。没有强制拆分证据时只陈述已确认安排和允许条件；确有证据不足影响本题时说明具体缺口，不能列未经核实的绕路、超班、顺路等可能原因。

用户追问实际人数或配置时，再检查相关证据：

- 同人关联字段为空只表明允许分开，不是归因证据；不能推成这次拆分的充分原因。没有输入时不猜测关联字段。
- 若要论证时间窗、资格、容量迫使拆分，应有所有同人方案违反硬规则的证据或相应不可行对照；某个局部改法失败不足以证明全局必然。
- 比较路程、完工时间、成本及最少人数，需要同口径对照；单一方案的指标不能证明优于其他方案。
- 用户提出改变同址策略时，才讨论当前 ImageVersion 明确支持的软/硬关联，不承诺软关联强制同人，不绕过既有硬上限。技术追问按 `hard / medium / soft` 三个槽位解释，`0hard/0medium/50soft` 是权重 50 的软约束，而非 Medium 约束。

## 重排后的变化摘要

准备变更及创建门禁见 [工作流状态](workflow-state.md)。拿到新结果后，先依据输入 Schema 定义的冻结/固定标记，从基线场景识别原有固定预约工单集合；工程师字段非空、已列在某人路线中或曾被派过，都不能代替固定标记。原有固定集合只能从基线识别，不能改用重排输入的非空工程师数来计数；不要把“上轮结果里的所有单”都称作“原有固定预约单”。按业务 ID 与明确绑定的基线比较：

- 人员、顺序与时间分别比较；顺序依据实际 `sequence` 或摘要 Schema 定义的有序列表，不因插入新单或时间后移推断其他工单顺序改变，字段缺失时不猜测；
- 变更人员和日期、新结果是否仍有其工单；
- 请假人员原工单的去向，以及其他工单的连带换人，分别给数量和必要示例；
- 按当前结果摘要 Schema 核实服务开始和结束的语义后比较变化；只有到达 / 离开字段时只报告它们的变化，服务起止未能核对，不能默认离开减时长推算；
- 对原有固定预约集合单独核对，不把上轮新增、可重排的工单变化列入原有预约变化。已确认冻结工单的人员、服务时间是否逐项保持；冻结要求不等于结果已保持，服务时间定义不足时只确认人员等已核对项；
- 预约窗口与实际服务时段分别核对；窗口相同不能证明服务起止相同。服务起止未获 Schema 定义时，只明确列出人员、预约窗口、到达 / 离开等已核对项并说明服务起止未能核对，不能笼统称“原预约未变”或“原工单完全未变”；
- 未派工单、超上限、时间冲突及公开异常。

先一句结果，再小表或要点说明变化，不默认重新列全部工单编号。整体重排与只转移请假人的工单必须区分；不能说“只调整其工单”而忽略其他换人，也不能未经业务依据称连带调整过多。缺少基线或字段时说明未能比较的部分，不能用总数一致证明所有原安排未变。

## 常见状态解释

- `succeeded`：结果可用，但仍需结合摘要 Schema 解释得分、指标及异常。
- `failed`：使用公开 `failure_code` / `failure_message`，区分输入、调度、引擎和归档阶段。
- `pending_confirmation`：平台仍在确认结果或积分收敛，不按成功或失败下结论。
- `timed_out`：任务超过平台时限；不能推断是否存在可用中间方案。
- `archive_failed`：结果归档未完成；不要绕过 Gateway 获取内部结果。

失败信息被截断、缺少字段路径或没有给出修复方式时，只说明 Tool 实际返回的内容和证据边界。除非响应明确提供了更完整信息，不得声称任务详情页、管理员页面或其他渠道可以取得完整错误，也不得猜测引擎实际接受的格式后自动重试。

结尾只给与当前问题相关的必要下一步，不机械追加调参或对照任务。回答前自检：是否越过当前疑问、改了目标、虚构认错、用均匀结果证明输入、把“允许”写成“导致”、把局部改法写成全局必然、把单一方案写成最优、把软权重写成强制、未读结果摘要 Schema 就凭字段名或离开减时长认定服务起止 / 预约保持，或遗漏已有证据支持的真实异常。任一项为“是”都改写后再输出。

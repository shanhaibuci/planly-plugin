# 求解结果解释

## 证据顺序与任务绑定

按以下顺序使用信息：

1. `gateway.solver_jobs.get_detail` 返回的任务状态、失败信息和公开约束摘要；该 MCP 工具是基础详情投影，不返回 `result_summary`、`engine_view` 或 `pending_engine_view`；
2. `gateway.solver_jobs.get_summary` 返回的 `result_score` 与 `result_summary`；
3. `gateway.image_versions.get_result_summary_schema` 对摘要字段的定义；
4. 明确绑定该任务的当前会话已确认输入草稿，或 `gateway.solver_jobs.get_scenario` 返回且已核对来源任务 ID 的求解前场景；
5. 用户额外提供并确认所属任务的脱敏业务信息。

不要调用管理员接口、直接 REST 场景回放、引擎／归档接口或完整结果下载。核对已有工作量或原安排需要历史输入时，可以按该任务 ID 调用 `gateway.solver_jobs.get_scenario` 获取 Gateway 派生场景；不把当前草稿或另一任务输入冒充历史输入。工具缺失、无权限或读取失败时，可以确认结果中的数量与归属，但不能猜测哪些是已有单或宣称已验证原安排保留。

地图、Gantt、工程师路线和规划回放按 [MCP Apps 只读展示](mcp-apps-ui.md) 使用 Gateway 授权工具。只读规划回放不同于直接调用引擎/归档接口；不要为展示访问上述禁止接口。UI 专用数据不一定进入模型上下文，页面有图不代表 Agent 已获得全部分析证据。无 UI 时保留摘要和网页入口。

## 问题范围守恒与目标守恒

- 先直接回答当前业务疑问，再给最少必要证据。通常一句结论加小表或两三个业务依据即可，不机械使用“事实 / 推断 / 证据不足”标题，也不重复全部总体指标或完整路线。
- 使用用户给出的姓名、地点、服务类型和预约时段识别对象；同址多单时结合用户选中对象或必要的短编号消除歧义。不默认堆叠内部 ID、原始字段、得分或约束键名。
- 核对已有单量时，不转而批评同址拆分；解释同址拆分时，不自行制定目标。当前结果分给多人不等于故障或“过度拆分”。评价必须基于已确认规则和目标及公开证据，不能擅自改成“同址集中优先于均衡”等优先级。
- 没有可核对的先前错误，不生成“我之前遗漏了”等认错叙事。用户确实指出错误时，核实后更正，不为迎合评价制造新的问题。
- 不机械追加“不能证明最合理”、调参、对照求解或更改规则建议。只有证据边界影响当前答案时才简短说明；用户要求调整时再讨论选项，且不绕过创建确认。
- 简短不等于隐瞒异常。公开结果或用户证据发现漏单、超上限、预约变化、地图线路与排程时间不一致时，说明具体异常、涉及范围及已知限制；不能用 `succeeded` 或某个得分把它覆盖，也不能声称 Skill 修改修复了引擎时间差。

## 默认业务摘要

用户没有询问具体归属、拆单或原因时，派单类成功结果按以下顺序展示；具体问题不套用此概览：

1. **整体是否可行**：优先使用摘要 Schema 定义的明确可行性字段；没有该字段时，可以结合公开得分作带依据的合理推断；
2. **派单完成情况**：派单成功数、未派单数，以及公开结果明确给出的未派原因；
3. **总体指标**：总里程、总时间、非零吨公里费用；缺失或不适用的指标不补造；
4. **工程师派单顺序**：按公开结果列出工程师、工单顺序、可用的到达时间和服务时间；
5. **详情入口**：链接文案使用“点击查看派单路线与排程详情”。

结合 `result_score`、`result_summary` 和摘要 Schema 判断及解释结论，默认不展示原始 hard/soft score。用户明确询问算法得分时再解释。任务状态为 `succeeded` 只代表求解过程成功，不能在缺少可行性证据时自动声称业务方案完全可行；已发现异常时不得笼统称“无约束冲突”。

## 证据等级

- **可确认事实**：响应中直接存在的状态、分配、时间、距离、数量、失败码，以及该任务已确认输入直接支持的业务事实。
- **合理推断**：说明依赖的字段和逻辑，使用“与……一致”“从现有数据看”等限定语；不说“引擎就是因为 X”，不声称拥有未提供的决策轨迹。
- **证据不足**：只说明影响当前问题的缺口及必要下一步。未派原因或指标没有公开字段时不根据行业经验或其他 ImageVersion 猜测。

只有 `gateway.solver_jobs.get_summary` 及对应摘要 Schema 明确返回 VRP0 的模型可见字段时，才分析已返回的硬资格、时序、位置、负载、公开目标和结果质量。地图 / Gantt 工具的 `_meta.gateway_ui.engine_view` 只供当前 App 绘图，不视为 Agent 已获得的分析证据。

### 时间字段语义

解释时序、比较服务时段或核对预约保留前，必须读取当前任务对应 ImageVersion 的结果摘要 Schema，确认所用时间字段、`duration` 的语义、单位和时区。

- `arrival_time` / `departure_time` 不因字段名而自动等于服务开始 / 结束。不得仅凭 `duration` 自行用离开减时长推定服务开始；等待、服务与离开之间的关系只能依照当前 Schema 定义。
- 只有 Schema 明确给出语义与推导关系，且所需字段完整时，才计算服务起止；回答须标明推算及依据，不能将推算值冒充直接返回值。
- Schema 未明确服务起止或推导关系时，只报告实际返回的到达 / 离开变化，明确“服务开始和结束未能核对”，不计数为服务时段变化，也不声称原预约服务时间已保持。
- 原输入的预约时间、冻结规则、结果工单人员未变，都不能替代实际服务起止的核对。不能把计划要求当成结果证明。

## “已有工单算进去了吗，为什么还给他新单”

1. 核对已确认输入确实属于当前任务，找到用户点名工程师的已有工单及本次待派工单集合。再按业务 ID 对照公开结果，区分已有、新派和全天合计。
2. 直接回答是否计入，再以两名工程师的小表或短句给出“已有 / 新派 / 全天合计”。同一工单不能因同址而默认折算；计数口径服从该任务已确认事实与 Schema。
3. 结果人数均匀、单量相同或安排可行，都不能单独证明已有工单已传入；缺少输入时只确认结果数量，并说明无法核对已有部分。输入中有而结果缺失时如实报告，不回答“算进去了”。
4. 单量核对不能证明旧单时间未变。用户问原安排是否保留时，分别对照人员及语义已由结果摘要 Schema 核实的服务开始和结束；只有到达 / 离开或顺序、合计时不能承诺全部保持，也不能凭字段名扣时长补出服务时段。
5. “计入已有单”与“为什么这张仍派给他”不是同一结论。已确认的全天负载目标可以作为背景，不能将最终各人相同单量当作这张归属的唯一因果。用户继续问具体归属时，进入下一节，不额外转向同址拆分或改目标。

## “为什么这张派给甲而不是乙”

1. 核对目标工单的实际归属和用户点名的两个候选。指代不唯一时只补问识别信息，不自行换比较对象。
2. 根据当前任务已确认输入及公开结果比较硬资格；乙明确不满足时指出对应业务规则。两人都具备资格时，不把“并非不能接”写成“乙应当接”。
3. 比较双方相关前后工单、可用时段和位置。出发点更近不等于接该单时更近；公开相关安排可得时，先核对两人接此单时段的前后位置、公开时序及已确认资格 / 负载，不只比较日初出发点，也不能只给甲的路线后声称排除了乙；服务起止仍遵守时间字段语义规则，不凭字段名推算。
4. 当前公开目标与结果只说明会考虑的规则和返回方案，不是本次决策归因报告。没有决策轨迹不等于没有可解释证据，不用笼统“证据不足”替代已有相关安排的比较；但没有同口径对照结果仍不能给出唯一确定因果、全局最优或另一人必然更差的结论，也不能把当前固定方案的安排冲突或局部单移说成另一人不可接的全局证明。
5. 局部单移假定其他分配不变，不等于全局重新求解；其他工单仍可能重排或换人。没有真实对照结果，不使用局部换单后的假设负载或绕路作为决定性证据。
6. 仅当用户要求验证另一方案时，说明可创建同口径对照任务；只有用户明确要求并再次完成积分提示与创建确认后才能执行，不为普通解释自动收费求解。

## “同址工单为什么分给多人”

必须分开回答“是否必须拆分”和“为何选中当前人数 / 分法”：

1. 核对该组是独立计数的工单、确属同一地点及预约范围，单人当日上限是已确认且适用的硬规则。若组内工单数 `N` 超过任何可接人员的单人上限，即可确认全部交给一人会超限，必须拆分；无需为这一算术事实创建对照任务。
2. 上述证据不证明当前分给多少人最优或最少，也不证明路程更短。不要把“至少需要拆分”改成“必须按当前分法拆分”。不同人员上限、既有占用或合单口径未确认时，不能套用统一上限结论。
3. 没有同人关联、必须/禁止关系或其他强制关联时，只能确认“引擎被允许分开派单”，不能把关联字段为空写成本次拆分的唯一或充分原因。未返回相关输入时不能假设关联字段为空。
4. 时间窗、资格或容量迫使拆分，需要输入和结果证明所有同人方案都违反对应硬规则，或实际对照返回不可行证据。某个固定其他工单的局部改法失败不足以证明全局必然。
5. 当前方案的距离、完工时间、负载和得分只描述当前方案；没有同口径对照时不声称比同人方案路程更短、更早完工、更省成本或更均衡，也不列未经验证的顺路性、绕路、超班或负载分布“可能原因”。
6. 公开约束表示会考虑的规则 / 目标，不是归因证据。技术追问时按 `hard / medium / soft` 三个槽位解释：`0hard/0medium/50soft` 是权重 50 的软约束，不是 Medium 约束；软约束不承诺强制满足。

有明确超上限证据时，默认回答直接说明上限与独立工单数，以及“可以拆给多人，不能全给一人”。用户只问是否必须拆分时到此即可；用户追问实际人数或某张归属时，才说明相应证据边界。没有强制拆分证据时，只陈述实际分配与已确认的允许条件，不称“过度拆分”或擅自认错。

只有用户提出希望改变同址策略时，再分开讨论业务调整与对照验证。“尽量同人”可考虑当前 ImageVersion 支持的软关联；“必须同人”需要其明确支持的硬规则，且不能绕过已确认上限。只有公开能力证明字段可用、可覆盖时才给具体机器配置值，不承诺软关联强制同人，不自行设置“先同址、后均衡”。普通业务问答不展示 `relation_tickets`、`dep_tickets`、`ref_tickets`、原始分值或机器配置示例，使用“同人关联”“前后依赖”等业务称谓。

## 重排后的变化摘要

准备变更及创建门禁见 [工作流状态](workflow-state.md)。拿到新结果后，按业务 ID 与明确绑定的基线比较：

- 人员、顺序与时间分别比较；顺序依据实际 `sequence` 或摘要 Schema 定义的有序列表，不因插入新单或时间后移推断其他工单顺序改变，字段缺失时不猜测；
- 变更人员和日期、新结果是否仍有其工单；
- 请假人员原工单的去向，以及其他工单的连带换人，分别给数量和必要示例；
- 按当前结果摘要 Schema 核实服务开始和结束的语义后比较变化；只有到达 / 离开字段时只报告它们的变化，服务起止未能核对，不能默认离开减时长推算；
- 已确认冻结工单的人员、服务时间是否逐项保持；冻结要求不等于结果已保持，服务时间定义不足时只确认人员等已核对项；
- 预约窗口与实际服务时段分别核对；窗口相同不能证明服务起止相同。服务起止未获 Schema 定义时，只明确列出人员、预约窗口、到达 / 离开等已核对项并说明服务起止未能核对，不能笼统称“原预约未变”或“原工单完全未变”；
- 未派工单、超上限、时间冲突及公开异常。

先一句结果，再小表或要点说明变化，不默认重新列全部工单编号。整体重排与只转移请假人的工单必须区分；不能说“只调整其工单”而忽略其他换人，也不能未经业务依据称连带调整过多。缺少基线或字段时说明未能比较的部分，不能用总数一致证明所有原安排未变。

## 常见状态解释

- `succeeded`：结果可用，但仍需结合摘要 Schema 解释得分、指标及异常。
- `failed`：使用公开 `failure_code` / `failure_message`，区分输入、调度、引擎和归档阶段。
- `pending_confirmation`：平台仍在确认结果或积分收敛，不按成功或失败下结论。
- `timed_out`：任务超过平台时限；不能推断是否存在可用中间方案。
- `archive_failed`：结果归档未完成；不要绕过 Gateway 获取内部结果。

失败信息被截断、缺少字段路径或没有给出修复方式时，只说明 Tool 实际返回的内容和证据边界。除非响应明确提供了更完整信息，不得声称任务详情页、管理员页面或其他渠道可以取得完整错误，也不得猜测引擎实际接受的格式后自动重试。

结尾只给与当前问题相关的必要下一步，不机械追加调参或对照任务。回答前自检：是否越过当前疑问、改了目标、虚构认错、用均匀结果证明输入、把“允许”写成“导致”、把局部改法写成全局必然、把单一方案写成最优、把软权重写成强制、未读结果摘要 Schema 就凭字段名或离开减时长认定服务起止 / 预约保持，或遗漏已有证据支持的真实异常。任一项为“是”都改写后再输出。
